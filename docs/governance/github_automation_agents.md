## Wiki Sync Behavior

Wiki publication is an owner-controlled operation. The local path and optional
manual-dispatch workflow use one committed source mapping and generator:

| Mechanism | Source | Behavior |
|---|---|---|
| Local owner publication | `scripts/github/Sync-Wiki.ps1` | Uses existing credentials, prepares and verifies pages, then publishes only when invoked with `-Publish`. |
| Manual GitHub Actions publication | `.github/workflows/wiki-sync.yml` | Refuses actors other than `flynn33`; requires a preconfigured `WIKI_OWNER_TOKEN` whose authenticated account is `flynn33`, uses owner commit identity and verifies non-force publication, remote commit SHA and local generated bytes. It does not run on `main` pushes. |
| Shared projection | `scripts/github/prepare_wiki.py` and `.github/wiki-sync.json` | Reads exact committed source blobs, builds configured direct/composite/index pages, pins repository links and preserves unmapped manual wiki pages. |

The generator preserves existing sidebar navigation and adds the specification
roadmap link once. Both publication paths validate the complete projection before
writes, verify generated bytes before publication, and retain local readback reports.
Publishers also compare the resulting commit SHA with remote master. A separate
remote clone and file-byte readback is recorded only when actually executed.
They do not delete pages, force-push, change protection settings or accept roadmap
gates. Manual wiki corrections are reviewed and published separately from the
configured source projection.

The optional workflow refuses missing or non-owner credentials before Git
operations. Its owner-token prerequisite is separate from the existing local
credential manager; the local route remains available without configuring or
dispatching a workflow. A configured secret or successful hosted publication is
reported only after its actual verification.

Phase 14 ability validation is registered in the canonical check catalog and is
reached through the same runner locally and in hosted workflows.

## Review Gates

Every pull request should preserve these gates:

```mermaid
flowchart LR
  PR["Pull request"]
  Main["Main CI"]
  Guard["Repository guardrails"]
  Forsetti["Forsetti compliance"]
  Identity["Contributor identity"]
  Review["Code review"]
  Merge["Merge"]

  PR --> Main --> Guard --> Forsetti --> Identity --> Review --> Merge
```

If any gate fails, inspect the workflow log, reproduce the failing command
locally when possible, and patch the smallest contract or documentation surface
that resolves the mismatch without weakening the guardrail.

## Throughput And Safety Limits

| Automation | Limit |
|---|---|
| Non-destructive package budget | Phase 12 and Phase 14 allow `0` deletions, `0` renames, `0` copies, and cap existing-file touches at `25`. |

## Operating Rules

- Automation validates repository truth; it does not invent canon.
- Wiki publication must preserve the current authority stack and accepted phase
  surfaces.
- Contributor identity checks are hard gates for protected branch hygiene.
- Non-destructive diff checks protect accepted package artifacts from silent
  removal or broad rewrites.
