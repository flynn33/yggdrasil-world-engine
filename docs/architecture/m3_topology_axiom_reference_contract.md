## 4. Topology identity, expansion and complete output

TopologyRequest retains request_reference, the complete origin_diagnosis, signed64 depth and explicit ASCII seed_token (default F). Supported depth is 0..6. Negative or excessive depth is rejected before any node construction. Topology source suitability is verified before expansion; no normalization or validity default is inferred.

Root is:
node_id=topology:<seed>:r; parent_id=null; depth=0; ordinal=0; branch_kind=root; path_token=r.

For parent path p, its ordered children have paths p0, p1, p2 and kinds continuation, positive, negative. IDs use the same seed and full path. Parent ID uses the seed and p. For path r followed by d digits, depth=d and ordinal is those digits interpreted in base three. Therefore depth-two paths are exactly r00,r01,r02,r10,r11,r12,r20,r21,r22, ordered 0..8; each parent and every ancestor can be reconstructed by deleting suffix digits. Seed grammar excludes ':' so ID components have no parsing ambiguity. Max path length is seven, max node ID forty-nine characters.

Expansion implements the canonical level-by-level ordered frontier behavior, creates the root and each child, and counts actual node constructions. It retains the next frontier until that level completes, then discards the previous frontier. On successful depth d, output contains exactly 3**d nodes, all at depth d and in ascending contiguous ordinal. visited_node_count equals 1+3+...+3**d and counts actual constructions, not an invented profiler sample. At d=6, the complete output is 729 leaves and 1,093 constructed nodes. The limit does not permit returning a requested depth-seven prefix as a complete topology.

TopologyResult retains request, exact policy, VERIFIED origin_validation, exact input_state, complete nodes, actual visited_node_count and one produced diagnostic. Its topology_reference is request_reference+':topology'; diagnostic reference is request_reference+':diagnostic:topology'. The result's owned construction rederives every node/path/parent/order/count rather than trusting metadata.

The success TopologyDiagnostic carries the request/topology references, actual state, seed, depth, frontier count, visited count, COMPLETE outcome, null failure and explained notes. It cites STRUCTURE, EXPANSION, ORDER, LINEAGE in that order. Rejected diagnostics cite ADMISSION only, have null successful topology/frontier references, zero constructed nodes, actual parsed state or null and the exact refusal. No failed result carries partial node output.

## 5. Explicit axiom subject and exact evaluation

AxiomSubject retains subject_reference, explicit AshState, relation_count, raw_measure, compressed_measure, scale_count, erasure_cost, self_reference_capable, self_model_available and AxiomSubjectProvenance. Counts/ticks are exact 0..9,223,372,036,854,775,807 integers. AxiomMeasure has ticks, unit and ticks_per_unit. Units are exactly STRUCTURE_TICK and ERASURE_TICK; tick scale is exact 1..1,000,000,000.

Provenance has the literal DECLARED_REFERENCE_INPUT, source_reference, method_id, method_revision and origin_diagnosis_reference. All these facts remain declared input. Their construction/consistency does not prove a method ran, an external source was measured, physical energy exists or a human authenticated them. No local compression routine, topology node count, bit count, semantic role or external provider is substituted.

Before evaluating any component, subject.state must equal the VERIFIED origin's parsed state; provenance origin reference must equal the origin's actual detection diagnostic reference. Raw/compressed units must both be STRUCTURE_TICK with equal ticks_per_unit; erasure must use ERASURE_TICK. Units are not converted. A mismatch produces one AXIOM SUBJECT rejection, retains all actual submitted subject/provenance and evaluates no components.

The five exact rules:
A1: relation_count > 0.
A2: compressed_measure.ticks < raw_measure.ticks (admitted same units and scale).
A3: scale_count > 1.
A4: erasure_cost.ticks > 0.
A5: self_reference_capable AND self_model_available.
Overall: A1 AND A2 AND A3 AND A4 AND A5.

No condition short-circuits later conditions. Each check immediately constructs AxiomCheckDiagnostic and GenerationDiagnosticRecord before evaluating the next check. Check payload retains the complete same immutable subject, axiom ID, factual passed, component current_impact, exact operator/operand names, explanation and optional overall_pass. A1..A4 overall_pass is null; A5 carries the actual conjunction and cites both SELFREFERENCE and CONJUNCTION. No sixth TEN is emitted.

AxiomDiagnostic preserves exactly its seven canonical fields: the five component booleans, overall_pass and five ordered explained notes. AxiomEvaluationResult is a complete evaluation even when overall_pass=false. It carries exact request/policy/VERIFIED validation, canonical summary and all five produced records. An evaluation refusal carries no summary or claimed component evaluations.

## 6. Diagnostic chain, severity, disposition and absence

GenerationDiagnosticRecord has exactly diagnostic_reference, existing source-owned TEN envelope and the narrow TopologyDiagnostic/AxiomCheckDiagnostic/AxiomInputDiagnostic payload union. It does not expand old DiagnosticEmission's producer domain or accept arbitrary payloads. New source kinds and stages cannot be used before their adoption. New generated summaries, notes and explanations equal the exact explanation_templates table in the business inventory, using only controlled enum/numeric facts and unsigned decimal/lowercase boolean formatting; they never echo raw seed, source labels or caller prose. Each new TEN has an independently checked compact ensure_ascii limit of 8,192 bytes; this adds no fictional smaller bound to old envelopes.

A coherent operation's first record parents the actual origin detection reference and shares its actual chain_root_reference. Every following axiom record parents the previous check and retains that same root. Existing ancestor severity is retained: each new envelope's severity is max(previous severity,current component impact). Thus a failing current-state origin may retain ERROR even if every measured axiom passes; passing axioms do not resolve that state fault.

Every new envelope subject_reference is the actual verified origin DETECTION.envelope.subject_reference, for topology completion/rejection and every axiom component/input refusal. The actual origin subject is retained across the PROCESSING chain with its root and actual parent prefix. Request, topology and declared AxiomSubject identities remain distinct typed payload facts; their equality to the origin subject is neither required nor inferred. This adoption correction to frozen R2 preserves the existing same-subject chain invariant without a source-transfer waiver. The new PROCESSING records cannot follow terminal disposition. Record/root/subject associations are structurally checked before a pure packet is returned and checked again before collector acknowledgment.

A1..A4 current impact is INFO for true, WARNING for false; disposition is RESOLVED for that true component and BLOCKED for false. The fifth check retains its independent A5 factual passed/current_impact, but its envelope also evaluates the conjunction. Fifth disposition is RESOLVED iff overall_pass, otherwise BLOCKED. An earlier false/A5=true result therefore has factual passed=true, current_impact=INFO, overall_pass=false and fifth disposition=BLOCKED, with cumulative WARNING or greater severity. Its explanation explicitly distinguishes the component and aggregate.

Topology success is INFO/RESOLVED over its admitted VALID origin; rejection is ERROR/BLOCKED with ancestor severity retained. Axiom input refusal is ERROR/BLOCKED with ancestor severity retained. Neither refusal fabricates recovery, containment, safe halt, authenticated authority or operational effects.

Record references are deterministically derived from the bounded request reference; check references use ':diagnostic:A1' through ':diagnostic:A5' and input refusal ':diagnostic:axiom-input'. If any required diagnostic reference collides with the origin or another member, refusal uses PendingGenerationDiagnostic rather than a cyclic/fabricated envelope. The pending record retains the desired reference/kind/rules, exact reason, missing requirements and failure code, but contains no TEN, guessed root or capture acknowledgment. Rejected validation, unsupported current source and unavailable validation use this same explicit missing-production form.
